## 📌 1. 프로젝트 개요
* **프로젝트명**: 나만의 파이썬 객관식 퀴즈 게임 (CLI)
* **개발 언어**: Python 3.10+ (외부 패키지 의존성 없이 표준 라이브러리 `random`, `datetime`, `json`만 사용)
* **실행 환경**: Windows / macOS / Linux 터미널 (Console)
* **주요 목표**:
  1. 함수와 클래스(OOP)로 코드를 역할별로 분리하고 모듈화
  2. `state.json`을 통한 데이터 영속성(Persistence) 및 파일 입출력 예외 처리
  3. 공통 입력 검증 헬퍼를 통한 비정상 종료(Crash) 방지
  4. 기능별 세분화된 Git 커밋(15개 이상) 및 브랜치 병합(`feat/play-quiz`) 이력 관리
  5. 5대 보너스 과제(랜덤, 문제 수 선택, 힌트, 삭제, 히스토리) 완벽 지원

## 💡 2. 퀴즈 주제와 선정 이유
* **퀴즈 주제**: **파이썬 첫걸음 입문 퀴즈**
* **선정 이유**:
  * 이번 미션은 단순히 프로그램을 제출하는 것보다, 직접 다시 구현할 수 있을 정도로 파이썬 기초를 익히는 데 목적이 있습니다.
  * 그래서 기본 퀴즈 5문제를 `print()`, 변수, 문자열, 리스트, `range()`처럼 **처음 파이썬을 배울 때 가장 먼저 만나는 핵심 개념**으로 구성했습니다.
  * 모든 문제에는 초심자를 위한 **힌트(Hint)**가 포함되어 있어, 단순 암기가 아니라 개념 복습용으로도 활용할 수 있습니다.
  * 추후 사용자가 원하는 어떤 주제든 메뉴 2번([퀴즈 추가])을 통해 무제한으로 문제를 등록할 수 있습니다.

|:---:|:---|:---|

## 📈 10. 퀴즈가 1000개 이상으로 늘어날 때의 한계와 대응 방안
현재 프로젝트는 `state.json` 파일 전체를 한 번에 읽고(`load_data()`), 전체를 한 번에 다시 저장하는(`save_data()`) 구조입니다.
입문 과제 규모에서는 단순하고 이해하기 쉽다는 장점이 있지만, 퀴즈 데이터가 1000개 이상으로 크게 늘어나면 아래와 같은 한계가 생길 수 있습니다.

### 예상 한계
1. **메모리 사용 증가**
   - 프로그램 시작 시 JSON 전체를 메모리에 올리므로 데이터가 커질수록 메모리 사용량도 함께 증가합니다.
2. **저장 속도 저하**
   - 퀴즈 1개만 추가하거나 삭제해도 파일 전체를 다시 저장하므로 데이터가 많아질수록 저장 시간이 길어질 수 있습니다.
3. **검색/조회 속도 한계**
   - 현재는 리스트를 순회하며 처리하는 구조이므로, 문제 제목 검색이나 특정 조건 필터링 기능이 추가되면 탐색 비용이 커질 수 있습니다.
4. **목록 출력 가독성 저하**
   - 1000개 이상의 퀴즈를 한 번에 출력하면 사용자가 원하는 문제를 찾기 어렵고 콘솔도 매우 길어집니다.

### 대응 방안
1. **인덱싱(Indexing) 고려**
   - 문제 ID 또는 질문 문자열을 key처럼 활용하는 딕셔너리 보조 구조를 두면 특정 문제를 더 빠르게 찾을 수 있습니다.
2. **페이징(Paging) 적용**
   - 퀴즈 목록 보기 기능을 10개 또는 20개 단위 페이지로 나누면 대량 데이터도 읽기 쉬워집니다.
3. **스트리밍/부분 로딩 고려**
   - 매우 큰 파일이라면 전체를 한 번에 메모리에 올리는 대신, 필요한 데이터만 부분적으로 읽는 구조를 고려할 수 있습니다.
4. **저장소 분리 또는 DB 전환**
   - 데이터가 계속 커진다면 JSON 단일 파일보다 SQLite 같은 경량 데이터베이스로 옮기는 편이 검색, 수정, 정렬에 더 유리합니다.
5. **검색 기능 전용 메서드 분리**
   - 향후 `search_quiz()` 같은 기능을 별도 메서드로 분리하면, 나중에 리스트 순회 → 인덱스 조회 → DB 질의 방식으로 교체하기 쉽습니다.

즉, 현재 구조는 **학습용·소규모 프로젝트에는 적합**하지만,
대규모 데이터 운영을 목표로 한다면 **인덱싱, 페이징, 부분 로딩, 데이터베이스 전환**을 차례대로 검토해야 합니다.

## 🛡️ 11. state.json 손상 시 복구 및 백업 전략
현재 구현은 `load_data()`에서 `try...except`로 JSON 파싱 실패를 감지하면,
기본 퀴즈 5종으로 자동 복원하는 방식을 사용합니다.
이 방식은 프로그램이 완전히 멈추는 것을 막는 데는 효과적이지만,
사용자가 직접 추가한 퀴즈를 되살리는 **명시적 백업 전략**까지 포함하고 있지는 않습니다.

### 현재 구현된 보호 방식
1. `state.json` 파일 존재 여부 확인
2. 파일 읽기 실패 또는 JSON 파싱 실패 감지
3. 경고 메시지 출력
4. 기본 퀴즈 데이터로 초기화 후 다시 저장

### 추가로 고려해야 할 백업 전략
1. **저장 전 백업 파일 생성**
   - `save_data()` 실행 직전에 기존 `state.json`을 `state.backup.json`처럼 복사해 두면,
     손상 발생 시 마지막 정상 버전으로 되돌릴 수 있습니다.
2. **버전별 백업 보관**
   - 날짜/시간을 파일명에 포함한 `state-2026-11-19-120000.json` 형식으로 보관하면,
     특정 시점 상태를 복원하기 쉽습니다.
3. **자동 백업 주기 설정**
   - 퀴즈 추가/삭제 시마다 즉시 백업하거나, N회 저장마다 백업하는 방식으로 운영할 수 있습니다.
4. **복구 우선순위 설계**
   - `state.json`이 깨졌을 때
     1) 최신 백업 파일 확인
     2) 백업 복원 시도
     3) 백업도 없으면 기본 데이터 초기화
     순서로 처리하면 사용자 데이터 손실을 줄일 수 있습니다.

### 현재 프로젝트 기준 권장 방향
입문 과제 범위에서는 기본 복구만으로도 충분하지만,
실제 사용성을 더 높이려면 **저장 전 백업 파일 생성**이 가장 먼저 추가할 만한 개선 포인트입니다.

## 🔧 12. 요구사항 변경 시 수정 포인트 정리
이 프로젝트는 파일별 책임이 비교적 분리되어 있어서,
요구사항이 바뀌더라도 어디를 먼저 수정해야 하는지 추적하기 쉽습니다.
아래는 대표적인 변경 상황과 우선 수정 대상입니다.

### 1) 점수 계산 방식이 바뀌는 경우
예: 문제마다 20점 고정, 오답 감점, 힌트 사용 시 30%만 지급 등

- **가장 먼저 수정할 위치**: `game.py`의 `play_quiz()`
- **이유**:
  - 현재 점수 계산은 `point_per_question`, `earned_points_total`, `final_score` 계산 로직이 모두 `play_quiz()` 안에 모여 있기 때문입니다.
- **함께 확인할 부분**:
  - 최고 점수 비교 로직 (`self.best_score` 갱신)
  - 플레이 기록에 저장되는 `score` 값

### 2) 퀴즈 구조가 바뀌는 경우
예: 선택지가 4개에서 5개로 늘어남, 주관식 문제 추가, 난이도 필드 추가

- **가장 먼저 수정할 위치**: `quiz.py`의 `Quiz` 클래스
- **이유**:
  - 문제 1개의 구조(질문, 보기, 정답, 힌트)는 `Quiz` 클래스가 정의하기 때문입니다.
- **함께 수정할 부분**:
  - `display()` 출력 형식
  - `is_correct()` 채점 방식
  - `to_dict()` / `from_dict()` 저장 형식
  - `game.py`의 `add_quiz()` 입력 방식

### 3) 저장 데이터 항목이 바뀌는 경우
예: 난이도, 카테고리, 문제 ID, 마지막 수정일 추가

- **가장 먼저 수정할 위치**:
  - `quiz.py`의 `to_dict()` / `from_dict()`
  - `game.py`의 `save_data()` / `load_data()`
- **이유**:
  - JSON에 어떤 필드를 저장하고, 다시 어떤 순서로 불러올지를 이 두 파일이 담당하기 때문입니다.

### 4) 기본 제공 퀴즈 세트가 바뀌는 경우
예: IT 상식 → 파이썬 입문 → Git 퀴즈 변경

- **가장 먼저 수정할 위치**: `default_data.py`
- **이유**:
  - 최초 실행 시 주입되는 기본 문제 목록을 여기서 관리하기 때문입니다.

### 5) 메뉴 구조나 사용자 흐름이 바뀌는 경우
예: 검색 메뉴 추가, 관리자 메뉴 분리, 점수 메뉴 위치 변경

- **가장 먼저 수정할 위치**: `game.py`의 `display_menu()`와 `run()`
- **이유**:
  - 사용자가 보는 메뉴 구성과 기능 분기가 이 두 메서드에 모여 있기 때문입니다.

정리하면,
- **점수 계산 변경** → `game.py > play_quiz()`
- **문제 구조 변경** → `quiz.py`
- **저장 형식 변경** → `quiz.py`, `game.py`
- **기본 문제 변경** → `default_data.py`
- **메뉴 흐름 변경** → `game.py`

이렇게 수정 포인트를 먼저 찾고 들어가면,
요구사항이 바뀌더라도 전체 코드를 처음부터 다시 뜯지 않고 필요한 부분만 빠르게 수정할 수 있습니다.
